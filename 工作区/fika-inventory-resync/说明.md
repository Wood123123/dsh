# Fika Inventory Resync v1.2.0

针对 **SPT 4.1.6 + Fika 2.4.4 / Fika.Headless 1.5.3** 的 BepInEx 补丁插件。
纯 Harmony 运行时补丁，不替换 Fika 任何文件，不改配置，删 DLL 即完全还原。

**两个独立根因，四个补丁：**

| 根因 | 补丁 | 症状 |
|---|---|---|
| **A. 库存操作被重复投递、应用两次** | 补丁 3（**仅主机**） | `Not enough space in target`(122) + `is not located at`(120) |
| **B. 切分堆叠时新物品 id 在各端各自生成** | 补丁 4（**所有端**） | `Cloned item ID desync` + `Could not find item*(52)` |

补丁 1/2 是配套的计数器重同步与空 id 守卫。

---

## 根因 B：卸载子弹时新分配的物品 id 在客户端与主机之间**必然不同**

这是玩家侧观察到的现象：**问题最常发生在把子弹从弹匣卸载出来的时候。**

### 机制（全部对着实机 `Fika.Core.dll` / `Assembly-CSharp.dll` 反编译确认）

**1. EFT 有两个 `IDatabaseIdGenerator` 实现，行为不一致**

```csharp
// 真实执行路径 —— 每调用一次就前进一格
ItemController.get_NextId:
    0002: ldfld   ItemController::_currentId
    0009: call    MongoID::op_Increment
    000E: stfld   ItemController::_currentId
    0013: ldloc.0        ← 返回自增【前】的值
    0014: ret

// 描述符回放路径 —— 永远返回同一个常量，永不前进，RollBack() 是空的
SplitOperationDescriptor/SplitIdGenerator.get_NextId:
    0001: ldfld   SplitIdGenerator::_nextId
    0006: ret
```

**2. 克隆物品时会按"物品 + 它的每一个内容物"反复取 id**

```
ItemManipulator::Split<T>  →  ItemExtensions::CloneItem<T>(T, IDatabaseIdGenerator)
CloneItemInternal:
    generator == null            →  MongoID.Generate(false)        // 全新随机 id
    generator is SameIdGenerator →  沿用原物品 id
    否则                          →  generator.NextId              // ← 计数器决定
    ...并对 StackSlot / Grid / Slot 里的每个内容物【递归】再取一次
```

**3. 是"合并"还是"切分"由**运行时的本地状态**决定**

```
ItemManipulator::ApplySingleItemToAddress(item, idGenerator, controller, to):
    005E: TransferMax(...)     ← 目标堆叠还放得下 → 只改数量，【不产生新 id】
    006E: Merge(...)
    0095: Split(...)           ← 放不下 → 切分，【产生新 id】
    00A4: Move(...)
```

**4. 而 `MoveOperationDescriptor` 只带 `ItemId | From | To | DestroyedItems` —— 完全不携带新分配的 id。**

**→ 结论：卸载子弹 = 把弹药堆叠从弹匣切分出来 = 分配一个新物品 id。Fika 只传"操作描述符"，每一端各自用自己的 `_currentId` 计数器去生成这个 id，因此必然不同。**

日志里 EFT **自带的** id 一致性检查已经响了：

```
[Error :Fika.Client] HandleInventoryPacket::Unable to process descriptor from netId 3,
  error: Cloned item ID desync. Expected ID: 6ac630c9147f66469b000059, real ID: 6ac630c9147f66469b000058
[Error :Fika.Client] HandleInventoryPacket::Unable to process descriptor from netId 3,
  error: Cloned item ID desync. Expected ID: 6ac630c8759c17dbc000007f, real ID: 6ac630c8759c17dbc0000079
```

**Expected 与 real 只差 1、差 6 —— 就是两端计数器相差的步数。**

### Fika 其实尝试过同步这个计数器

```
CoopGame.cs:268         ControllerId = fikaPlayer.InventoryController.CurrentId   ← 发起方上报
CoopHandler.cs:470      QueueProfile(..., firstId, firstOperationId, ...)
ObservedPlayer.cs:346   new ObservedInventoryController(player, profile, true, firstId, ...)
ObservedInventoryController.cs:32   _currentId = firstId;                        ← 镜像用它播种
```

**镜像的 `_currentId` 就是它的物品 id 生成器**，Fika 在开局时用发起方的值播种过一次。
但只要**任何一次应用失败 / 被重复投递 / 被空包 resync 清成 `default`**，计数器就永久失步，
之后**每一次切分都会在所有机器上产生不同的 id**，而那些 id 再也找不回来 —— 这就是
`Could not find item with id` / `Could not find item owner with id` 的来源。

**→ 所以补丁 3（去重，让各端应用的次数一致）、补丁 4（回放生成器按同样规则前进）、
补丁 1/2（失败后重同步计数器、禁止清空）必须一起上。**

## 根因：库存操作在非发起方客户端上被**应用两次**

### 证据链（全部对着你实机那个 `Fika.Core.dll` 反编译验证）

**1. 客户端发送时会写 broadcast 字节，主机不会**

```
FikaClient::SendGenericPacket    IL 0x0012:  NetDataWriter.Put(System.Boolean)   ← 写
FikaServer::SendGenericPacket    IL:         没有 Put(Boolean)                    ← 不写
```

`ClientInventoryController.RunClientOperation` 发库存操作时传的是 `broadcast: true`：

```csharp
FikaPlayer.PacketSender.NetworkManager.SendGenericPacket(in packet, DeliveryMethod.ReliableOrdered, true);
```

**2. 主机因此转发两遍**

```csharp
// FikaServer.OnNetworkReceive
if (reader.GetByte() == 1)
    _netServer.SendToAll(reader.GetRemainingBytesSpan(), deliveryMethod, peer);   // ← 转发 #1（原始字节）

switch (reader.GetEnum<EPacketType>()) { ... case Generic: HandleGenericPacket(reader, peer); }

//  → FikaServer.OnInventoryPacketReceived
if (result.Failed) { ...发 resync...; return; }
...
SendGenericPacket(in packet, DeliveryMethod.ReliableOrdered, true, peer);          // ← 发送 #2（同一个描述符）
```

**3. 客户端不读 broadcast 字节，所以两份包布局完全相同、各解析一次**

```csharp
// FikaClient.OnNetworkReceive
public void OnNetworkReceive(...)
{
    switch (reader.GetEnum<EPacketType>())   // ← 直接读包类型，没有 broadcast 字节
```

**结论：每一个库存操作，在每一个非发起方客户端上都会被重放两次。**

### 这如何解释你日志里的每一条错误

重复应用一个**已经应用过**的操作，产生的正是：

| 日志错误 | 次数 | 机制 |
|---|---|---|
| `Not enough space in target` | 122 | 第一份已经把格子/堆叠占掉了，第二份没地方放 |
| `item X is not located at <A>. It's at <B>` | 120 | 第一份已经把 X 从 A 移到 B，第二份还在找 A |
| `Could not find item owner with id: X` | 33 | 第一份已经改了父节点，`GameWorld.ToItemAddress` 查不到 |
| `Could not find item with id: X` | 19 | 同上 |
| `<cell> is taken by another item` | 8 | 第一份已占位 |

实测分布：`Not enough space in target` 在 netId 3 上重复 **79** 次、netId 2 上 **43** 次 —— 完全无区分度的重复，正是同一操作被反复重放的特征。

而 `LogOutput(1).log` 里每一条 `is not located at` 的"现实位置"**都恰好是该操作的目的地** —— 铁证。

### 附带修好的第二个问题

主机**拒绝**一个操作时（`result.Failed`）会 `return`，**不做**发送 #2 —— 但转发 #1 **已经发出去了**。
于是其他客户端会应用一个主机明确拒绝的操作 → 主机镜像与客户端镜像直接分叉。

抑制转发 #1 之后：拒绝的操作不再泄漏给其他客户端。

## 四个补丁

| # | 位置 | 作用 |
|---|---|---|
| **3（根因 A）** | `FikaServer.OnNetworkReceive`（Transpiler，**仅主机**） | 把该方法的 broadcast 标志读取换成辅助函数：若是 `Generic` / `InventoryOperation` 则返回 0（不转发），其余包型行为不变。全方法**只有 1 个** `NetDataReader.GetByte()` 调用点，已静态核对。 |
| **4（根因 B）** | `EFT.SplitOperationDescriptor/SplitIdGenerator.get_NextId`（Prefix，**所有端**） | 让回放用的 id 生成器像 `ItemController.get_NextId` 一样**前进**（返回当前值、存回自增后的值），而不是永远返回常量。目标类型 `NestedPublic`、getter `public`、`MongoID.op_Increment` `public static`，均已核实。 |
| 1 | `ObservedInventoryController.CreateOperationFromDescriptor`（Postfix，客户端） | 重放失败时广播一个空 `ResyncInventoryIdPacket(netId)` 求助；主机转发给该 netId 的持有者，持有者用原生 `IsYourPlayer` 分支回自己的 `CurrentId`，主机再转发回来纠正各方镜像（= 把失步的 id 计数器重新对齐）。带 per-netId 冷却（默认 1s）。 |
| 2a | `FikaServer.OnResyncInventoryIdPacketReceived`（Prefix，主机） | `MongoId` 为空则跳过。空包语义是"请求"而非"赋值"，无条件 `SetNewID` 会把镜像 `_currentId` 清成 `default`，等于把 id 生成器归零。 |
| 2b | `FikaClient.OnResyncInventoryIdPacketReceived`（Prefix，客户端） | 同上，但目标是**自己的玩家**时放行，否则求助就没人应答。 |

判空用 `MongoID.Equals(default(MongoID))`。已核实 `MongoID.Equals` 只比较 `_timeStamp` + `_counter`，而 Fika 的 `PutMongoID`/`GetMongoID` 也只传这两个字段 —— 精确判据。

> **不要只装补丁 3。** 去重只消除根因 A；根因 B 的 id 失步需要补丁 4，而计数器一旦失步需要补丁 1/2 才能拉回来。

## 部署

`FikaInventoryResync.dll` 放两边同一个位置：

```
<EFT>\BepInEx\plugins\FikaInventoryResync\FikaInventoryResync.dll
```

- **补丁 3 只需要装在主机（无头端）** —— 主机是唯一执行转发的地方。
- **补丁 4 必须装在所有端**（主机 + 所有客户端），因为它修的是每一端各自的回放路径。
- 补丁 1/2 是客户端功能，装了的客户端才受益。

**同一 GUID 只能存在一份。** 如果你在 `plugins\` 根目录下也放了一份 `FikaInventoryResync.dll`，请删掉，只留子文件夹里那一份。

## 已知限制

- **未实机联机验证。** 结论全部来自源码 + 实机 DLL 反编译的静态推导；每个补丁的挂载点都已逐一核对唯一无歧义，但实际效果需要你跑一局看日志。
- Transpiler 依赖 `OnNetworkReceive` 的结构。Fika 升级后若该方法重写，补丁会**明确报错并保持惰性**（不会误改语义），届时需重新核对。
- **根因 B 只能"对齐"，不能根治。** 就算各端计数器完全同步，Fika 用的仍是"广播操作描述符、各端各自重放"这套模型 —— 它要求各端物品树逐字节一致。只要有一个 mod 改了物品树、或一次应用被丢弃，就会再次失步。真正根治需要改协议层（让每个操作携带它新分配的 id）。补丁 1/2 的作用是让失步能**被拉回来**，而不是让它不发生。
- 主机玩家自身没有"求助"路径。
- 与 `FikaIdResync` 功能重叠，建议只留一个（本插件已包含其思路的正确实现）。

## 配置

`<EFT>\BepInEx\config\com.local.fikainventoryresync.cfg`

| 项 | 默认 | 说明 |
|---|---|---|
| `General / Enabled` | `true` | 总开关 |
| `General / RequestCooldownSeconds` | `1.0` | 同一 netId 两次求助的最小间隔 |
| `General / Verbose` | `true` | 详细日志 |

## 怎么确认生效

启动日志（搜 `FikaInventoryResync`）：

```
[Info :FikaInventoryResync] FikaInventoryResync v1.2.0 loaded. Enabled=True Cooldown=1
[Info :FikaInventoryResync] Patch1 OK: client resync request hooked on ...ObservedInventoryController::EFT.InventoryLogic.IOperationHandler.CreateOperationFromDescriptor
[Info :FikaInventoryResync] Patch2a OK: host resync guard on FikaServer::OnResyncInventoryIdPacketReceived
[Info :FikaInventoryResync] Patch2b OK: client resync guard on FikaClient::OnResyncInventoryIdPacketReceived
[Info :FikaInventoryResync] Patch3 OK: host inventory-operation de-duplication transpiler on FikaServer::OnNetworkReceive
[Info :FikaInventoryResync] Patch3: replaced the broadcast-flag read (1 call site, as expected).
[Info :FikaInventoryResync] Patch4 OK: split replay id generator now advances (was returning a constant) on EFT.SplitOperationDescriptor/SplitIdGenerator::get_NextId
```

**判定标准**：客户端 `HandleInventoryPacket::Unable to process descriptor` 应从三百多条**降到接近 0**，
`Cloned item ID desync` 应完全消失。如果任何 `Patch*` 行报 `SKIPPED` / `expected exactly 1 ... but found N`，
补丁会明说且保持惰性（不会误改语义），请把该行发我。
